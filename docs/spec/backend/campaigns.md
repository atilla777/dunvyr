# Кампании: домен, идемпотентное создание, присоединение по приглашению, членство, отзыв, REST-контракт

> Подтверждённое поведение, введённое Beads-задачей dunvyr-u4k.2 (веха «Два гостя входят в одну кампанию», срез организатора) и расширенное задачей dunvyr-u4k.3 (гостевой срез: присоединение по ссылке, членство, отзыв приглашения). Нормативные источники: [multiplayer-and-access](../../product/multiplayer-and-access.md) §Кампания и встреча, §Организатор, §Приглашения, [security-and-privacy](../../rules/security-and-privacy.md) §Гостевой вход, §Контроль доступа, [bounded-contexts](../../rules/bounded-contexts.md) (владение campaigns, public-only потребление identity), [architecture](../../rules/architecture.md) (идемпотентность, конкурентность), [backend-and-data](../../rules/backend-and-data.md) §REST и WebSocket, §API contracts. Слой-прецедент и инфраструктура — [identity](identity.md), [backend/skeleton](skeleton.md).

## Домен campaigns (`dunvyr/campaigns/domain/`)

- `CampaignName` (замороженный VO): обрезка по краям, 1–60 Unicode-символов, без символов категории `C*` (управляющие/невидимые форматные). Нарушение — `InvalidCampaignName`. Правила приняты в задаче (локальная деталь по «Ограничение детализации»): продуктовое имя кампании обязательно, уникальность не требуется.
- `MaxSeats` (замороженный VO): целое 2–20 включительно, default `DEFAULT_MAX_SEATS = 6`; bool/float/строка отклоняются (`InvalidMaxSeats`). Организатор — обычный участник и занимает место; инвариант агрегата: `len(members) <= max_seats`.
- `Invitation` (замороженный VO): хранит **только** SHA-256 hex-хэш секрета (`hash_invitation_secret`); сырой секрет не живёт в доменном объекте. `Invitation.issue(secret)` хэширует свежий секрет и не сохраняет сырец; `revoke()` возвращает копию с `revoked=True` (immutable), `is_active = not revoked`. Невалидный хэш (не lowercase 64-hex) отклоняется инвариантом.
- `Membership`: `guest_id: UUID`, `nickname: str` (**снапшот** на момент вступления — список участников не читает таблицы identity), `role: organizer|player`, `joined_at` (timezone-aware).
- `Campaign` (Entity, замороженный dataclass): ровно **один** участник с ролью organizer, и он совпадает с `organizer_id` (инвариант `InvalidCampaign`); участники уникальны по `guest_id`; `idempotency_key: UUID`; `invitation: Invitation`; `created_at` timezone-aware. `Campaign.create(...)` создаёт кампанию с единственным участником-организатором; `revoke_invitation()` — копия с отозванным приглашением; `join(guest_id, nickname, now)` — членство гостя (введено u4k.3, ниже).
- Секрет приглашения: `secrets.token_urlsafe(32)` (256 бит, ~43 URL-safe символа) — тот же класс энтропии, что сессионный токен identity.

### Join-инварианты агрегата (u4k.3, TDD)

`Campaign.join(guest_id, nickname, now)`:

- гость уже участник → возвращает **тот же агрегат без изменений** (идемпотентный replay; место не занимается); на уровне агрегата replay не требует активного приглашения и свободных мест. На сервисном уровне членство проверяется после активности приглашения, поэтому повторное открытие отзыванной ссылки возвращает `404`, а доступ действующего участника сохраняется через `GET`/экран кампании;
- новый участник требует: активное приглашение (`InvitationInactive`), свободное место (`CampaignFull`), псевдоним, уникальный в кампании — точное, case-sensitive сравнение со всеми членами, включая организатора (`NicknameTaken`); все три ошибки — подклассы `InvalidCampaign`;
- успех — копия агрегата с новым `Membership(role=player, nickname=<снапшот псевдонима гостя из сессии>, joined_at=now)`.

Локальные детали, принятые в u4k.3 (по «Ограничение детализации»): **без временного истечения приглашения** — единственная деактивация отзыв (модель `Invitation` не расширена); **уникальность псевдонима в рамках кампании enforced** (коллизия отображаемых имён — предмет членства кампании, отложенный из identity); смена псевдонима не существует — гостю с занятым псевдонимом нужно войти заново под другим именем.

## Игровая встреча: кандидат dunvyr-lbp.1

Локальный проверенный кандидат: интеграция и независимое ревью ожидаются, публикация в main не подтверждена. Основание: [права организатора и встреча](../../product/multiplayer-and-access.md), [продолжение игры](../../product/gameplay.md), Task `dunvyr-lbp.1` и [ADR транзакции](../../rules/architecture/adr/game-session-transaction.md).

- Начальное состояние кампании — `{revision: 0, session: null}`. `start` создаёт `running`, только если предыдущей встречи нет или она `ended`. Переходы: `running → paused` (pause), `paused → running` (resume), `running|paused → ended` (end); остальные отклоняются. Новая встреча не удаляет предыдущую, кампанию, персонажей или данные приключения. Revision увеличивается на каждом переходе и не обнуляется между встречами.
- `GET /api/campaigns/{campaign_id}/game-session` доступен члену кампании и возвращает `{revision, session}`; `session` — `null` или `{id, status, started_at, ended_at}`. Организатор отправляет `POST /api/campaigns/{campaign_id}/game-session/start` или `POST /api/campaigns/{campaign_id}/game-session/{session_id}/{pause|resume|end}` с `Idempotency-Key: <uuid>` и строгим телом `{"expected_revision": <неотрицательное целое>}` без дополнительных полей. Новый start — `201`, остальные успехи и replay — `200`; ответ добавляет `replayed`.
- Сервер проверяет членство при чтении и роль организатора при каждой команде, включая replay: аноним/не-член/игрок без права управления — `403 forbidden`, отсутствующая кампания — `404 not_found` после аутентификации; некорректные UUID, тело или действие — `422`. Несовместимый переход/неактуальный ID встречи — `409 invalid_action`; устаревшая revision — `409 stale_state`, повтор ключа с другим payload — `409 conflict`. Мутации защищены Origin и отдельным in-process rate limit (`429`, `Retry-After`).
- Receipt ограничен `(campaign_id, actor_id, key)` и фиксирует action, target и expected_revision: точный повтор возвращает исходный, возможно уже устаревший снимок без нового события; отличающийся payload конфликтует до проверки revision. При неизвестном результате клиент повторяет ту же команду с тем же ключом.
- Миграция `0008` создаёт `campaigns_game_sessions` (история, CHECK статуса и partial UNIQUE одной `running|paused` встречи на кампанию), `campaigns_session_state` (revision, текущая встреча, CHECK revision ≥ 0) и `campaigns_session_receipts` (составной PK ключа); существующие кампании получают revision 0. SQLite write-lock перед чтением и CAS revision дополняют ограничения БД. Состояние/revision читаются одним joined SELECT.
- В `campaigns.public` доступны immutable `GameSessionSnapshot`, `GameSessionState`, `GameSessionChanged` и протоколы `GameSessionReader`, `GameSessionEventStager`, `GameSessionNotifier`. Composition root передаёт owning adapters одну транзакционную Session: campaigns сохраняет состояние и receipt, communication только ставит в транзакцию свою запись события; commit/rollback принадлежит campaigns UoW. Уведомление идёт отдельно после commit; его ошибка не отменяет запись. Контракт потока и восстановления — [communication](communication.md).

Проверки кандидата: `test_game_session_domain.py` (TDD 11 RED → 11 GREEN), `test_game_session.py` (ACL, ошибки, replay, rollback, доставка, сохранение данных), `test_game_session_persistence.py` (независимые соединения, ограничения БД, restart, migration/backfill, согласованное чтение). Координатор сообщил `make lint` exit 0; компоненты gate: 254 unit, 25 import, 72 frontend, 148 integration прошли в `make test-ci`, где 2 из 12 E2E упали на rate limit настройки гостей; после исправления только E2E helper отдельный `make test-e2e-smoke` прошёл 12/12 и lint exit 0. Полный gate интегрированного снимка ещё предстоит.

## Присутствие: кандидат dunvyr-lbp.2

Локальный проверенный кандидат, интеграция и независимое ревью ожидаются. Основание — [presence и отключения](../../product/multiplayer-and-access.md), Task `dunvyr-lbp.2`, [границы контекстов](../../rules/bounded-contexts.md) и [ADR lease](../../rules/architecture/adr/presence-leases.md).

`campaigns` владеет синхронизированным process-local состоянием соединений, а `communication` через `campaigns.public` сообщает об авторизованных подключениях, отключениях и продлении lease. Online агрегируется по кампании и гостю: закрытие одной из нескольких вкладок не отключает гостя; после последнего разрыва действует grace 5 с, повторное подключение его отменяет. Lease соединения — 30 с; истечение и grace рассчитываются от дедлайна, фоновый sweeper с шагом 1 с работает независимо от запросов UI. Значения — локальные defaults кандидата. Состояние не сохраняется в БД и не меняет членство; новый runtime начинает с новым epoch и без старых соединений. Multi-worker не поддерживается; игровые последствия отключения не реализованы. Транспорт, проверки и ограничения описаны в [communication](communication.md).

## Публичный контракт (`campaigns/public/`)

Расширен задачей dunvyr-u4k.4 (первый потребитель — communication, см. [communication](communication.md)): только ORM-free immutable snapshots и Protocols, без внутренних слоёв.

- `CampaignMemberSnapshot` / `CampaignSnapshot` (замороженные dataclass): стабильный вид члена/ростера кампании для других контекстов.
- `CampaignMembershipReader` (Protocol): `find_member(campaign_id, guest_id) → CampaignMemberSnapshot | None` — единственный способ проверки членства чужим контекстом; реализация `SqlAlchemyCampaignMembershipReader` живёт в campaigns infrastructure поверх собственного репозитория.
- `CampaignEventPublisher` (Protocol): post-commit порт `member_joined(campaign_id, member)` для доставки факта вступления в real time; вызывается **только после commit** join-транзакции и не может её откатить. Реализацию (адаптер communication) вяжет composition root — campaigns не импортирует communication, цикла public API нет.

## Application и потребление identity

- `CampaignService.create_campaign(command)`: предварительный поиск по `(organizer_id, idempotency_key)` — найденное возвращается как replay (`created=False`, **без** секрета); иначе доменная валидация, генерация секрета, `Campaign.create`, запись. Гонку закрывает БД-ограничение: `DuplicateIdempotencyKey` → перечитывание победившей записи (защита от повторов на уровне схемы, не только Python).
- `CampaignService.get_campaign(campaign_id, viewer_id)`: отсутствующая кампания → `CampaignNotFound`; не-член → `CampaignAccessDenied` (представление — ниже). Членство проверяет сервер в каждой операции.
- `CampaignService.join_campaign(command)` (u4k.3): секрет хэшируется (`hash_invitation_secret`), кампания ищется по `invitation_token_hash`; неизвестный секрет или неактивное приглашение → `InvitationUnavailable` (без раскрытия существования); уже член → replay `joined=False` без записи; иначе доменный `join` и вставка членства с БД-защитой гонок (ниже). Идемпотентность join — семантикой `(guest, campaign)`: Idempotency-Key заголовок не требуется, повтор команды того же гостя не создаёт дубль. С задачей dunvyr-u4k.4 успешный первый join **после commit** публикует `member_joined` через опциональный порт `CampaignEventPublisher` (см. выше); replay повторную публикацию не выполняет, ошибка доставки логируется и никогда не ломает закоммиченный join (доставка — [communication](communication.md) §Доставка строго после commit).
- `CampaignService.revoke_invitation(campaign_id, actor_id)` (u4k.3): не-организатор (аноним/не-член/член-не-организатор) → `CampaignAccessDenied` — серверная проверка роли; уже отозванное приглашение → идемпотентный возврат текущего view без записи; иначе `update_invitation` + commit.
- Порты: `UnitOfWork` (репозиторий кампаний: `find_by_invitation_token_hash`, `add_member_if_seats_available`, `update_invitation`), `Clock`, `IdFactory`, `InvitationSecretGenerator` (Protocol).
- Rate limit create: отдельный от identity in-process скользящий лимитер `CampaignSlidingWindowRateLimiter` — **свой бакет**, 10 запросов / 60 c per client IP, lock-защищённый, сбрасывается рестартом (принятое ограничение однопроцессного MVP, как у identity). Join (u4k.3): второй такой же бакет per app (`app.state.campaign_join_rate_limiter`, 10/60 c per client IP, per-app ленивая инициализация в campaigns presentation — composition root не менялся; локальный UTC-clock, чтобы не импортировать внутренний слой identity). Revoke использует бакет create.
- Потребление identity — **только** `dunvyr.identity.public`: `GuestResolver` (резолв гостя по сырому токену cookie) и `SESSION_COOKIE_NAME`. Публичный контракт identity расширен аддитивно константой `SESSION_COOKIE_NAME = "dunvyr_session"` (единый источник истины: identity presentation импортирует её из public, см. [identity](identity.md)); campaigns не импортирует внутренние слои identity и не обращается к его таблицам — гости ссылаются opaque UUID-текстом без cross-context FK. Join создаёт членство **только** для гостя из cookie-сессии; ссылка-приглашение не даёт владения чужой сессией/персоной (в теле запроса нет и не принимается guest_id).

## REST-контракт (`campaigns/presentation/`, префикс `/api/campaigns`)

- `POST /api/campaigns` body `{"name": "...", "max_seats": 6}` (max_seats optional, default 6) + обязательный заголовок `Idempotency-Key: <uuid>` (клиент генерирует; отсутствие/не-UUID → `422`). Первый create → `201` с полным представлением кампании и **одноразовыми** `invitation.secret` + `invitation.path = "/join/<secret>"`; повтор тем же ключом того же организатора → `200`, та же кампания, `secret/path = null`, дублей не создаёт. Невалидные name/max_seats → `422` с текстом доменной ошибки. Аноним (нет/истекла сессия) → `403`. Защиты: Origin-проверка (allow-list, иначе `403`), rate limit (свой бакет, `429` + `Retry-After`). CORS allow-headers расширен `Idempotency-Key`.
- `POST /api/campaigns/join` body `{"secret": "<непустая строка>"}` (u4k.3). **Секрет — в теле запроса, не в URL**, чтобы не попадать в access-логи; невалидное тело → `422`. Первый join → `201` + `CampaignResponse` (состав включает нового игрока; секрет приглашения в ответе отсутствует всегда); повтор тем же гостем → `200` + то же представление (replay, дубля членства и места нет). Аноним → `403 forbidden`; неизвестный **или отзыванный** секрет → `404 not_found` (без раскрытия существования приглашения); нет мест → `409 campaign_full`; псевдоним уже занят в кампании → `409 nickname_taken`. Защиты: Origin-проверка, отдельный join-бакет rate limit (`429` + `Retry-After`). Секрет сравнивается только по SHA-256 хэшу, не логируется (проверено caplog) и не фигурирует в текстах ошибок.
- `POST /api/campaigns/{campaign_id}/invitation/revoke` (u4k.3): только организатор — аноним/не-член/член-не-организатор → `403 forbidden`, несуществующая кампания → `404 not_found` (контракт существования как у GET). Успех и повторный отзыв уже отозванного → `200` + `CampaignResponse` с `invitation.active=false`. Защиты: Origin-проверка, бакет create (rate limit).
- `GET /api/campaigns/{id}` — только членам: несуществующая → `404` `detail: "not_found"`; аноним или не-член → `403` `detail: "forbidden"` (без раскрытия существования). Ответ никогда не содержит секрет приглашения (только `invitation.active`). После отзыва действующие члены читают кампанию как раньше.
- Схема ошибок следует [backend-and-data](../../rules/backend-and-data.md) §API contracts: `not_found`/`forbidden` в `detail` + специфичные коды конфликтов `campaign_full`/`nickname_taken` для `409` (фронтенд показывает по ним понятные сообщения); имя кампании в UI-сообщениях фронтенда.

## Миграции и персистентность

- Бизнес-миграция `0003` (после identity `0002`): `campaigns_campaigns` (`id` TEXT PK, `name` TEXT, `max_seats` INTEGER, `organizer_id` TEXT + индекс, `idempotency_key` TEXT, `invitation_token_hash` TEXT **UNIQUE**, `invitation_revoked` BOOLEAN, `created_at` TEXT; `UNIQUE(organizer_id, idempotency_key)`) и `campaigns_members` (PK `(campaign_id, guest_id)`, FK → `campaigns_campaigns.id` ON DELETE CASCADE + индекс, `nickname` TEXT, `role` TEXT, `joined_at` TEXT). Префикс `campaigns_` — владение контекста (ownership-тест); UUID/datetime — TEXT (isoformat), как в identity.
- Бизнес-миграция `0004` (u4k.3): `UNIQUE(campaign_id, nickname)` (`uq_campaigns_members_campaign_id_nickname`) на `campaigns_members` — БД-защита уникальности псевдонима от гонок; SQLite не умеет добавлять table constraint in-place, поэтому `batch_alter_table` (перестройка таблицы). Метаданные SQLAlchemy синхронны с миграцией (unit-тест метаданных).
- Гонки join закрыты на уровне БД (u4k.3, паттерн «домен валидирует — схема защищает»): (a) тот же гость — PK `(campaign_id, guest_id)`; (b) места и активность приглашения — `add_member_if_seats_available`: единый atomic `INSERT … SELECT … WHERE (SELECT COUNT(*) FROM campaigns_members …) < (SELECT max_seats …) AND invitation_revoked IS false` (rowcount 0 → сервис сбрасывает snapshot и перечитывает: участник → replay, неактивное приглашение → `404`/`InvitationUnavailable`, иначе `campaign_full`); (c) псевдоним — `UNIQUE(campaign_id, nickname)`; `IntegrityError` → `MembershipInsertConflict` → перечитывание: конфликт с самим гостем → replay `200`, чужой псевдоним → `nickname_taken`.
- Авто-миграция `DUNVYR_AUTO_MIGRATE=1` (make dev, E2E) поднимает схему до head (с u4k.4 — `0005`, бизнес-миграция communication); integration-тесты — собственный Alembic-pipeline. Схема только Alembic, не `create_all`.
- Персистентность проверена: файловая SQLite (tmp_path), два экземпляра приложения — после «рестарта» кампания и состав читаются, `alembic_version=head` (`0005` на снимке u4k.4).

## Архитектурные контракты

- Скелетный контракт «независимость контекстов» заменён (задачей u4k.2) на **запрет импорта чужих внутренних слоёв** (domain/application/infrastructure/presentation всех семи контекстов): межконтекстные импорты **только** через `public/` — первая реальная пара campaigns→identity.public легитимна по правилу bounded-contexts. Wildcard-контракт «чужие domain/application/infrastructure» сохранён.
- Добавлены 4 контракта campaigns (по образцу identity): слои `presentation > application > domain` и `infrastructure > application > domain`; запрет `campaigns.public` импортировать внутренние слои; запрет `campaigns.domain` импортировать внешние слои. С задачей dunvyr-u4k.4 добавлены аналогичные 4 контракта communication — итого **16** контрактов, все зелёные; unit-тест архитектуры дополнительно фиксирует, что единственные межконтекстные импорты campaigns — `dunvyr.identity.public` (а `public/` campaigns потребляет communication).
- Ownership: metadata campaigns содержит только `campaigns_*`; создание кампании не меняет счётчики строк identity-таблиц (интеграционные тесты).

## Фронтенд-срез

- Срез организатора (u4k.2): после входа (`App`) форма «Название кампании» + кнопка «Создать кампанию» (`CreateCampaignForm`, блокировка при отправке, ошибки с `role="alert"`) → экран кампании (`CampaignScreen`): заголовок, «Мест занято N из M», ссылка-приглашение (абсолютный URL `window.location.origin + path`) с кнопкой «Скопировать ссылку» и статусами `role="status"`/`role="alert"`, панель «Участники». Секрет живёт только в состоянии экрана после create; повторный GET его не возвращает.
- Гостевой срез (u4k.3): путь `/join/<secret>` разбирается без роутера (`joinPath.ts` — regex + `decodeURIComponent`, роутинговая библиотека не вводилась). Аноним на `/join` сначала видит `LoginForm`, после входа — экран присоединения `JoinScreen`: кнопка «Присоединиться» (блокировка при отправке) и понятные ошибки `role="alert"` («Ссылка-приглашение не найдена или отозвана», «В кампании нет свободных мест», «Этот псевдоним уже занят в кампании», rate limit, сеть). Успех → показ `CampaignScreen` + `history.replaceState('/')`.
- Восстановление последней кампании (u4k.3, включает fix review-low L2 из u4k.2): после create/join фронтенд помнит id последней кампании гостя в localStorage `dunvyr:campaign:<guestId>` (id — не секрет: доступ по-прежнему требует сессионную cookie). При загрузке после аутентификации — `fetchCampaign(id)`: `200` → `CampaignScreen` (организатор видит обновлённый состав после F5 — механизм «у создателя — после обновления»; повторная отправка формы создания не порождает вторую кампанию); `403/404` → ключ удаляется, обычный flow (создание или join по пути). Использована ранее неиспользуемая `fetchCampaign`.
- `CampaignScreen` роль-зависим (u4k.3): список участников у обеих ролей («— организатор», «(вы)»); секция приглашения — только организатору (`campaign.organizer_id === currentGuestId`): при активном приглашении — ссылка/копирование (пока секрет известен в этом экране) и кнопка «Отозвать ссылку» (→ состояние «Ссылка отозвана», ошибки `role="alert"`); игрок-не-организатор секцию приглашения не видит. Компонент монтируется с `key={campaign.id}` — смена кампании пересоздаёт состояние.
- `api.ts`: `createCampaign(name, {maxSeats, idempotencyKey})`, `joinCampaign(secret)`, `revokeInvitation(campaignId)`, `fetchCampaign(id)` и типы; idempotency-key генерируется клиентом через `crypto.getRandomValues` (v4-UUID вручную — работает в insecure LAN HTTP, где `crypto.randomUUID` недоступен; крайний fallback `Math.random`); `ApiError` несёт HTTP-статус для restore-логики.

## Проверки на введённом снимке

Срез u4k.2: `make lint` и затронутый набор зелёные (исполнитель и координатор независимо): **120** backend unit (campaigns: домен 34, service, tables, tokens, architecture + identity без изменений), **12** import-контрактов, **16** frontend Vitest (4 файла), **48** integration (campaigns REST 21: идемпотентность/чтение только членом/секрет не повторяется/негативные «секрет не в логах» (caplog)/rate limit/ownership/миграции; персистентность двумя экземплярами), **2** E2E smoke (desktop+mobile, сценарий не менялся).

Срез u4k.3: `make lint`, `make test-unit`, `make test-integration` зелёные (исполнитель и координатор независимо): **143** backend unit (+23: домен 42 с join-инвариантами TDD, service с четырьмя гоночными сценариями join, tables с UNIQUE-метаданными), **12** import-контрактов, **31** frontend Vitest (5 файлов: +`JoinScreen`, расширены `App`/`CampaignScreen`), **61** integration (+13: `test_campaigns_join` — состав у обеих ролей/чужой 403, replay без места, `campaign_full`, `nickname_taken`, неизвестный+отзыванный секрет → `404` при сохранении доступа действующих, аутентификация/Origin/тело, «секрет не в логах и ответах» (caplog), отдельный join-бакет (create работает после исчерпания join), revoke только организатором/идемпотентен/сохраняет доступ/404/аноним; `test_campaigns_members` — атомарность seat-check и проверки активности приглашения одним SQL-утверждением, отзыв блокирует вставку, дубликат псевдонима отклоняется БД; миграции/персистентность — head `0004`, FK с `ON DELETE CASCADE` переживает batch-перестройку). ## Ограничения (ещё не существует)

Исключение участника (kick) и игровые ходы ещё отсутствуют; presence и lifecycle встречи — локальные срезы выше, не игровой движок. Чат/WS-доставка и live-обновление состава описаны в [communication](communication.md). Секрет приглашения невосстановим: одноразовая выдача в ответе create, при потере ответа ссылку не показать снова. Смены псевдонима нет: гостю с занятым в кампании псевдонимом нужно войти заново под другим именем; сравнение псевдонимов case-sensitive (Unicode case-folding не делается). Списка «мои кампании» нет — восстановление одной последней кампании через localStorage, навигация по нескольким кампаниям вне среза. Rate limit per-process, multi-worker не поддерживается; join-бакет инициализируется лениво per app. В dev-потоке весь LAN делит один join-бакет (10/60 c per client IP) через Vite-прокси с одного loopback-адреса. `shared` не используется.

## Очередь и жизненный цикл встречи

Кандидат `dunvyr-lbp.4`: pause/end приостанавливают существующую очередь, resume или новая running-встреча продолжают её без сброса; состояние presence остаётся эфемерным. Gameplay использует публичные порты campaigns для транзакционной блокировки lifecycle и защищённого снимка presence. Подробности и ограничения — [gameplay](gameplay.md).
