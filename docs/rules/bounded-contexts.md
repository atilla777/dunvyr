# Bounded Context first

## Главный принцип

**Сначала предметные области, потом слои внутри каждой.** Один modular monolith — единый процесс FastAPI, общий SQLite-файл, один Git-репозиторий, но логически независимые контексты. Python `packages` выполняют роль namespaces. Изоляция позволяет независимым задачам/агентам изменять минимальную область кода, но сама по себе не гарантирует отсутствия конфликтов при одновременной работе.

## Начальная карта областей

| Пакет | Владеет | Не владеет |
| --- | --- | --- |
| `identity` | Гостевая идентичность, серверные сессии, аутентификация | Членством в кампании, самим персонажем |
| `campaigns` | Создание кампании, состав/права, ссылки, встречи, presence, административные команды | Правилами боёв, знаниями NPC |
| `characters` | Персонаж, атрибуты/навыки, HP, состояния, инвентарь, XP, ограничения использования персонажа | Очередью хода, сценарным сюжетом |
| `adventures` | Авторский сценарий, версии, сцены, локации, известные факты, переходы, журнал открытий, состояние прохождения | Расчётом бросков/урона |
| `gameplay` | Данными испытаний в ходе игры, очередь/раунды, ProposedAction, резолюция проверок, бой, голосование маршрута* | Записью HP напрямую, изменением чужих таблиц |
| `communication` | Сообщения, чат-поток, синхронизация событий, доставка | Назначением сюжетных исходов, изменением доступности речи |
| `narration` | Вызов LLM, описание результатов, речь NPC, смысловое сопоставление, prompt-контракты | Состоянием персонажей, произвольным выбором исходов |

`*` Голосование может оказаться лучше внутри `campaigns` при детальном проектировании, поскольку это согласование участников; **выбрать единственного владельца в ADR перед реализацией**, не дублировать состояние в двух областях. Аналогично ответственность за `Encounter` (template в `adventures`, runtime в `gameplay`) оформить явным контрактом. Эти две границы — предмет уточнения, не повод отказываться от остальных изоляционных правил.

**Не называть каждый технический модуль Bounded Context автоматически:** `communication` может быть сервисной областью, а `gameplay` — ключевым доменом; глубина DDD зависит от сложности, не от формального шаблона.

## Зависимости

- Внешнему контексту доступен только его `public/` (DTO, Protocol, команды/запросы, события), никакие `domain/`, `infrastructure/`, `application/internal/` или ORM модели другого контекста не импортируются.
- Обращение по чужим ORM-таблицам и изменение данных напрямую **запрещено**, даже если импорт формально разрешён.
- Контекст не может владеть инвариантом, который фактически исполняется другой областью без публичного контракта.
- Избегать циклов между публичными API; при появлении цикла пересмотреть контракт, порядок координации или границы.
- `shared` — только малые универсальные технические примитивы (например, clock, ID, result), **не общая свалка Entity/Service**.
- Публичные контракты можно версионировать/расширять; изменение требует оценки существующих потребителей и контрактных тестов.

## Полезное разделение ответственности

Пример: `gameplay` вычисляет попадание и предлагает `DamageTarget`; `characters` применяет урон через свою публичную операцию и обеспечивает `HP >= 0`, `unconscious` и связанные инварианты. Координирующий application use case выполняет связанные операции в согласованной транзакции. `adventures` разрешает сюжетный результат, но не устанавливает HP напрямую. `communication` отправляет результат клиентам только после commit.

## Независимость агентов

До изменения определить owning context и подписчиков публичного контракта. Не проводить широкую реорганизацию по всем пакетам ради локальной Task. Новые междоменные контракты определять и проверять **до** зависимых работ; использовать native Beads `blocks` только для реальных prerequisites. Параллельные изменения одного контракта требуют координации — директории не заменяют контроль конкурентной записи.
