# Frontend-скелет: toolchain, минимальная страница, dev-сервер, проверки

> Подтверждённое поведение, введённое Beads-задачей dunvyr-68c.2 (bootstrap-веха 1). Нормативные источники: [technology-and-infrastructure](../../rules/technology-and-infrastructure.md), [frontend](../../rules/frontend.md), [testing](../../rules/testing.md). Канонический fresh-clone flow — в корневом `README.md`.

## Toolchain и команды

- Версия Node — единственный источник истины: корневой `mise.toml` (`node = "24.22.2"`); `.nvmrc`/`engines` не используются (решение владельца 2026-11-05). Пакетный менеджер — npm в составе mise-Node.
- Все инструменты проверок (Vite, TypeScript, ESLint, Prettier, Vitest, Testing Library) — devDependencies `frontend/package.json`; точные версии — в `frontend/package-lock.json`. React/react-dom — единственные runtime-зависимости.
- Свежий клон: `mise install` → из `frontend/`: `npm ci` → проверки.
- Реальные команды проверок (из `frontend/`, все зелёные на снимке задачи):
  - `npm run lint` — ESLint 9 flat config (`typescript-eslint` recommended, `eslint-plugin-react-hooks`, `eslint-plugin-react-refresh`);
  - `npm run format:check` — Prettier 3 `--check` (lock/dist/coverage/node_modules исключены через `.prettierignore`);
  - `npm run typecheck` — `tsc --noEmit` (strict, `noUnusedLocals`/`noUnusedParameters`/`verbatimModuleSyntax`);
  - `npm run test` — `vitest run`;
  - `npm run build` — `tsc --noEmit && vite build` (production-сборка; `dist/` игнорируется Git).
- Публичный командный интерфейс — корневой `Makefile` (включая `make test-unit` с `npm run test`) — см. [tooling/commands](../tooling/commands.md); состав gate — в [testing](../../rules/testing.md).

## Минимальная страница

- Точка входа: `frontend/index.html` — `<div id="root">` + module-скрипт `/src/main.tsx`; `main.tsx` монтирует `App` в `StrictMode`, отсутствие `#root` — явная ошибка времени выполнения.
- `App` — срез гостевого входа (введён задачей dunvyr-u4k.1, контракт API — [backend/identity](../backend/identity.md)): при загрузке `GET /api/identity/me` → состояния `loading` («Проверяем сессию…») / `anonymous` (форма входа: label «Псевдоним», input, кнопка «Войти», ошибка с `role="alert"`) / `authenticated` («Вы вошли как …»). Заголовок `<h1>Dunvyr</h1>` присутствует во всех состояниях (контракт E2E smoke). С задачей dunvyr-u4k.2 после входа показывается срез организатора кампаний (контракт — [backend/campaigns](../backend/campaigns.md)): форма `CreateCampaignForm` («Название кампании» + «Создать кампанию») → экран `CampaignScreen` (ссылка-приглашение с копированием, панель участников). С задачей dunvyr-u4k.3 добавлены гостевой flow и восстановление: путь `/join/<secret>` разбирается минимально (`joinPath.ts`, без роутинговой библиотеки — Vite dev отдаёт SPA fallback) → `JoinScreen` (успех/отказ с понятной ошибкой); после create/join id последней кампании гостя хранится в localStorage (`lastCampaign.ts`) и при загрузке восстанавливается через `fetchCampaign` (F5 возвращает на экран кампании с актуальным составом; 403/404 очищают ключ); `CampaignScreen` роль-зависим (секция приглашения и кнопка «Отозвать ссылку» — только организатору). С задачей dunvyr-u4k.4 в `CampaignScreen` добавлен real-time чат (контракт — [backend/communication](../backend/communication.md)): `ChatPanel` размещён до секций приглашения/участников (mobile-приоритет), после подписки WS грузит историю через `fetchChatHistory`, live-события — через `chatSocket.ts` (same-origin WS), `chat.ts` дедуплицирует по `event_id` и сортирует по `sequence`, события `member_joined` live-добавляют участников в ростер экрана (счётчик мест обновляется без перезагрузки); с задачей dunvyr-u4k.5 `chatSocket.ts` получил bounded reconnect-протокол (5 попыток, backoff 500–8000 мс; после каждого open — resync через snapshot-курсор `after`, буферизация live-кадров до завершения snapshot; после исчерпания окна — честный offline) и статус `reconnecting` (loading/stale/offline-индикация `aria-live`) — детали протокола в [backend/communication](../backend/communication.md) §Фронтенд-срез и reconnect-протокол клиента. API-клиент — `src/api.ts` (относительный `/api`); продуктового роутинга (кроме `/join`) и стилевой темы нет. Стили — минимальный `index.css` (центрирование, типографика, светлая/тёмная схема через `prefers-color-scheme`, адаптив форм входа/кампании/присоединения, стили чата: свои/чужие сообщения, системные строки).

## Выбор приключения

`AdventurePanel` на экране кампании загружает [состояние приключения](../backend/adventures.md). Пока выбор не сделан, все участники видят ожидание, а организатор — каталог, предупреждение об окончательности выбора и кнопки выбора. Пустой каталог показывается явно. После выбора участники видят название, описание и fingerprint версии; участник не видит кнопок выбора. Ошибки показываются с возможностью обновить состояние; при конфликте или устаревшем fingerprint каталог сбрасывается. Ожидающее состояние обновляется каждые 5 секунд в видимой вкладке и при возвращении к ней; запросы не заменяют более свежий результат. E2E проверяет выбор, обновление у участника без потери черновика чата, F5 и повтор после ошибки загрузки.

## Собственный персонаж

`CharacterPanel` загружает собственную карточку и шаблоны ([контракт](../backend/characters.md)). Пока приключение не выбрано, показывает ожидание и повторяет запрос каждые 5 секунд; после выбора предлагает имя, внешность и архетип. Выбор архетипа инициализирует распределение его значениями; форма показывает характеристики, навыки и их фиксированную привязку, допустимые границы, потраченный и оставшийся бюджет. При превышении бюджета показывает ошибку и блокирует создание; сброс или смена архетипа возвращает распределение к шаблону, текст при смене сохраняется. При ошибке создания сохраняет черновик для повтора; при ошибке начальной загрузки предлагает повтор. После создания показывает имя, архетип, внешность, характеристики и навыки; редактирования и удаления нет. Component-тесты проверяют расчёт, границы, сброс, отправку распределения и сохранение черновика; E2E проверяет двух настроенных персонажей и чат после reload в desktop и mobile-эмуляции.

## Стартовая сцена

Кандидат `dunvyr-kye.4` (интеграция ожидается): `SceneViewer` независимо от персонажа читает [стартовую сцену](../backend/adventures.md). При ожидании повторяет запрос каждые 3 секунды; ошибка загрузки допускает повтор и не отключает чат. На desktop сцена и постоянно смонтированный `ChatPanel` стоят рядом; на mobile над чатом находится компактная карточка с кнопкой полноэкранного viewer. Изображение показывается целиком, доступны увеличение/уменьшение/сброс и прокрутка увеличенного полотна. Hotspot-кнопки дублируются полным списком объектов; выбор показывает уже доступное описание, не запускает игровую команду. Тексты выводятся как текст, не HTML.

Диалог имеет доступное имя, удерживает клавиатурный фокус, закрывается кнопкой и Escape с возвратом фокуса кнопке открытия. Черновик и выделение чата сохраняются; фоновые запросы не отбирают его фокус. Ошибка картинки оставляет описание/список объектов и повтор загрузки. Component-тесты покрывают состояния/тексты/ошибки; desktop/mobile Playwright проверяет настоящую загрузку изображения, соседство сцены/чата, фокус диалога, touch-прокрутку и объекты с целями не менее 44 px, отсутствие горизонтального переполнения страницы и reload. Реальное мобильное устройство и его экранная клавиатура этим прогоном не проверены. Игровые действия остаются вне среза.

## Начальная карта

Кандидат `dunvyr-kye.5` (интеграция ожидается): `LocationMap` читает только [отфильтрованную сервером карту](../backend/adventures.md), показывает текущую, посещённую и обнаруженные комнаты и известные выходы. Для каждого выхода с неизвестной целью создаётся отдельная локальная заглушка, без группировки по тайной цели. Граф дополняют текстовые списки комнат и выходов; управление масштабом и прокрутка доступны с клавиатуры и сенсора. На mobile карта открывается отдельно в диалоге с закрытием кнопкой или Escape и возвратом фокуса. Ожидание повторно запрашивается через 3 секунды, при ошибке доступен повтор; чат остаётся смонтированным и черновик сохраняется. Перемещения или открытия карта не выполняет.

`LocationMap.test.tsx` и desktop/mobile Playwright проверяют состояния и взаимодействия; совместный smoke двух гостей охватывает выбор, персонажей с бюджетной настройкой, общие сцену и карту, чат и reload. Эмуляция Chromium не заменяет проверку на реальном телефоне и LAN-приёмку владельца.

## Просмотр испытаний

Кандидат `dunvyr-lbp.3` (публикация ожидается): `EncounterCatalog` рядом со сценой и картой читает [безопасный каталог испытаний](../backend/adventures.md#шаблон-испытания-и-безопасный-каталог). Показывает названия, описание очевидных способов, навык, фиксированную характеристику и авторскую сложность как текст и семантические списки. Кнопок исполнения нет; явно указано «Выполнение действий пока недоступно.». Без сценария виден экран ожидания с повтором каждые 3 секунды, в старой закреплённой редакции — «Доступных испытаний нет.». После готового ответа опрос прекращается. Ошибка допускает явный повтор; смена кампании или unmount отменяет запрос и не позволяет устаревшему ответу подменить каталог.

`EncounterCatalog.test.tsx` проверяет загрузку, безопасный текст, метаданные, отсутствие команд, пустой каталог, повтор и отмену устаревших запросов. Desktop/mobile сценарий `e2e/adventure.spec.ts` проверяет у обоих гостей «Нестабильный терминал» и два способа, отсутствие кнопок исполнения и сохранение чата/черновика. Это просмотр, не начало испытания, бросок или применение исхода; реальный телефон и LAN-приёмка остаются за владельцем.

## Игровая встреча

Кандидат `dunvyr-lbp.1` (интеграция и независимое ревью ожидаются): `GameSessionPanel` показывает участникам серверный статус встречи; только организатор видит допустимые кнопки начала, паузы, продолжения и завершения. При конфликте клиент обновляет состояние и просит проверить действие; при неизвестном результате сохраняет команду и ключ для явного повтора. Component-тесты `GameSessionPanel.test.tsx`, `CampaignScreen.test.tsx`, `ChatPanel.test.tsx` и desktop/mobile smoke `e2e/game-session.spec.ts` проверяют срез; фактические результаты кандидата приведены в [campaigns](../backend/campaigns.md). Это не подтверждение LAN-приёмки на реальных устройствах; ходы и AI вне среза встречи.

## Присутствие участников

Кандидат `dunvyr-lbp.2` ожидает интеграции и независимого ревью. Список участников показывает «В сети» или «Не в сети» по полному серверному presence snapshot/live, а до синхронизации и при разрыве — «Статус неизвестен», не выдавая устаревшие данные за актуальные. Несколько вкладок одного гостя агрегируются сервером; после перезапуска новый epoch принимается из snapshot при восстановлении. `ChatPanel` и `chatSocket` буферизуют live до snapshot, отсеивают старые revision и отвечают на heartbeat. Контракт, проверенные сценарии и результаты кандидата — в [communication](../backend/communication.md); desktop/mobile Playwright использует эмуляцию Chromium, не заменяющую LAN-приёмку владельца на реальных устройствах. Очередь, автопропуск, AI и kick не входят в этот срез.

## Dev-сервер и LAN

- `npm run dev` поднимает Vite dev-сервер на `localhost` по умолчанию.
- LAN-биндинг — явный opt-in: переменная окружения `DUNVYR_DEV_HOST` (LAN-IP или `0.0.0.0`) в `vite.config.ts` задаёт `server.host`; по умолчанию не `0.0.0.0` (правило LAN: открытие listener — только после осознанной настройки firewall и allowed origins). LAN-запуск обоих серверов одной командой — `make dev` (слушает `0.0.0.0` по умолчанию) — см. [tooling/commands](../tooling/commands.md).
- Прокси API (введён задачей dunvyr-u4k.1): `vite.config.ts` проксирует `/api` → `DUNVYR_BACKEND_ORIGIN` (default `http://127.0.0.1:8000`); с u4k.4 запись дополнена `ws: true` — тот же префикс проксирует и WebSocket-апгрейд чата (`/api/campaigns/{id}/chat`). Браузер всегда работает с API same-origin на адрес Vite-сервера — cookie сессии и Origin-проверки остаются корректными с любого LAN-хоста без перечисления origin'ов на frontend.
- Проверено на снимке задачи: dev-сервер отдаёт `GET /` → 200 (HTML с root-контейнером и module-скриптом) и `GET /src/main.tsx` → 200 (Vite-трансформированный модуль с React-mount).

## Очередь испытания

Кандидат `dunvyr-lbp.4`: `QueuePanel` показывает испытание, раунд, порядок, текущего и пропущенных участников; при исчерпанной очереди — ожидание online игроков. При running-встрече и открытом соединении участник со своим персонажем может начать доступное испытание, а текущий игрок — обменяться с более поздним online-участником. Пауза, завершение и синхронизация отображаются явно. Конфликт обновляет очередь; при неизвестном результате доступен явный повтор с тем же ключом. Исполнение действий отсутствует. Контракт, проверки и ограничения — [gameplay](../backend/gameplay.md); desktop/mobile E2E используют эмуляцию, не заменяющую приёмку на устройствах.

## Подготовка предложений

Кандидат `dunvyr-lbp.5` ожидает повторного ревью после исправления и интеграции. В каталоге очевидный способ выбирается кнопкой «Подготовить»; секция с доступным именем «Мои предложения» показывает только личные сохранённые варианты, а недоступный выбор — без скрытых деталей. Для готовности нужны открытое соединение, running-встреча, загруженные очередь, предложения и персонаж; редактирование и отмена доступны только в собственный ход. UI предлагает замену другим способом того же испытания, серверный контракт шире. Видны предупреждение о будущей перепроверке, состояния загрузки и ошибки (`role="alert"`); выполнение и подтверждение отсутствуют.

При личном уведомлении и reconnect запрашивается REST; ответы и replay объединяются только по возрастанию версии. При 409 клиент обновляет предложения, очередь и встречу и просит проверить действие; при неуспешном обновлении просит обновить страницу. При неизвестном результате сохраняет команду с ключом для явного повтора. При 429 команда также остаётся ожидающей с исходными ключом и телом, новые команды блокируются; пользователю предлагается повторить позже, при числовом `Retry-After` показываются секунды. Автоматического ожидания или повтора нет. Чат остаётся смонтированным: desktop/mobile E2E проверяет сохранение черновика и фокуса при изменении из другой вкладки, reload, несколько предложений, изменение и отмену. Проверки и границы — [gameplay](../backend/gameplay.md#проверки-среза); Chromium-эмуляция не подтверждает поведение экранной клавиатуры или доступность на реальном устройстве.

## Подтверждение действия

Кандидат `dunvyr-lbp.6`, интеграция ожидается, дополняет и заменяет прежние ограничения выше об отсутствии исполнения: собственное доступное предложение можно подтвердить в свой ход при синхронизированном соединении и running-встрече. UI показывает серверные кубики, сумму и успех/неудачу в общем потоке, обновляет сцену, цель, каталог, очередь и личные предложения; терминальная очередь показывается завершённой. После потери ответа или 429 сохраняются исходные ключ и версии для явного повтора; конфликт вызывает обновление состояния. Reload/reconnect восстанавливают сохранённый результат; чат остаётся доступным. Нет оптимистического назначения результата клиентом, AI или боя. Контракт, результаты проверок и ограничения — [gameplay](../backend/gameplay.md#подтверждение-и-небоевой-результат).

## Описание ведущего

Кандидат `dunvyr-lbp.7`, интеграция ожидается, дополняет предыдущее ограничение об отсутствии AI: после результата `ChatPanel` показывает отдельную визуально отличимую запись «Ведущий» в общем потоке. Для `pending` и `generating` видны разные состояния ожидания, для `ready` — сохранённый текст как текст, не HTML; при `failed` сообщается, что результат сохранён и игру можно продолжить, и доступна кнопка «Повторить описание». Ошибка повтора показывается через `role="alert"`; во время запроса кнопка блокируется, для той же revision сохраняется ключ повтора. Клиент объединяет события по correlation/revision, игнорирует устаревшие состояния и восстанавливает текущую запись из snapshot даже вне страницы истории. Чат и черновик остаются доступны. Контракт, сообщённые проверки desktop/mobile и ограничения — [communication](../backend/communication.md#описание-сохранённого-исхода-кандидат-dunvyr-lbp7).
