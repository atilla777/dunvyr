# Командный интерфейс: Makefile, make dev, git hooks, E2E, CI, изоляция прогонов

> Подтверждённое поведение, введённое Beads-задачами dunvyr-68c.3, dunvyr-68c.4 и dunvyr-68c.5 (bootstrap-веха 1). Нормативные источники: [testing](../../rules/testing.md), [technology-and-infrastructure](../../rules/technology-and-infrastructure.md), [development-workflow](../../rules/development-workflow.md). Канонический fresh-clone flow — в корневом `README.md`.

## Публичный интерфейс команд

- Корневой `Makefile` — единственный публичный интерфейс локальных команд (нормативно: [testing](../../rules/testing.md)). Все цели выполняют команды через `mise exec -- ...`, поэтому `mise activate` не обязателен; требуются Linux, GNU make и mise в PATH. Версии рантимов — единственный источник истины `mise.toml` (см. [backend/skeleton](../backend/skeleton.md), [frontend/skeleton](../frontend/skeleton.md)).
- Цели и их состав (актуальная таблица — в [testing](../../rules/testing.md)): `make setup` (mise install + `uv sync` + `npm ci` + установка Chromium для Playwright), `make lint`, `make test-unit`, `make test-integration`, `make test-e2e-smoke`, `make test-e2e-full`, `make test-ci`, `make test-affected`, `make dev`, `make hooks`, `make help`.
- `make test-affected SCOPE=<backend|frontend|all> ARGS='<селекторы>'` — честная передача нативных селекторов (pytest пути/`-k`/`-m`; паттерны файлов Vitest), собственного `--changed`/dynamic-селектора нет. `SCOPE` по умолчанию `all` (одни и те же `ARGS` в оба стека); пустой `ARGS` или неизвестный `SCOPE` — usage-ошибка с exit 2. Подтверждено: `SCOPE=backend ARGS='tests/unit/test_app.py'` → 3 passed против 6 в полном `-m unit`.
- Изоляция прогонов: backend-тесты выполняются на in-memory SQLite в своём процессе (файлов рабочей БД не создают), `TestClient` без сетевых портов, frontend unit — jsdom без браузера (см. [backend/skeleton](../backend/skeleton.md)); E2E изолирован отдельно (см. ниже). `RUN=<id>` на тест-целях задаёт отдельный pytest cache (`-o cache_dir=.pytest_cache/run-<id>` внутри игнорируемого `.pytest_cache/`). Подтверждено: параллельные `make test-unit RUN=p1` и `make test-integration RUN=p2` — оба зелёные.

## `make dev`: LAN-запуск одной командой

- `scripts/dev.sh` поднимает backend (`uvicorn --factory dunvyr.main:create_app`) и frontend (Vite через `DUNVYR_DEV_HOST` + `--port`), печатает локальные и LAN-адреса и предупреждения: listener `0.0.0.0` требует firewall только для доверенной LAN; обычный HTTP — только доверенная LAN (для интернета обязателен HTTPS); cookie сессии HttpOnly/SameSite=Lax, `Secure` выключен для локального HTTP (включается `DUNVYR_COOKIE_SECURE=1`); миграции Alembic применяются при старте.
- С u4k.1 `dev.sh` передаёт процессам: backend — `DUNVYR_ALLOWED_ORIGINS` (LAN-IP + `127.0.0.1` + `localhost` на порту frontend; добавляется и явный `DUNVYR_DEV_HOST`, если задан отдельный хост) и `DUNVYR_AUTO_MIGRATE=1` (файл `backend/dunvyr.db` создаётся/обновляется Alembic-миграциями, не `create_all`); frontend — `DUNVYR_BACKEND_ORIGIN=http://<host>:<backend_port>` (target Vite-прокси `/api`, контракт — [frontend/skeleton](../frontend/skeleton.md)). Политика origins/CSRF — [backend/identity](../backend/identity.md).
- Слушатель по умолчанию — сознательный `0.0.0.0` (решение задачи 68c.3: `make dev` — LAN-режим; raw `npm run dev` остаётся на localhost — см. [frontend/skeleton](../frontend/skeleton.md)). Переопределения: `DUNVYR_DEV_HOST` (например `127.0.0.1`), `DUNVYR_BACKEND_PORT` (8000), `DUNVYR_FRONTEND_PORT` (5173). При `DUNVYR_DEV_HOST=127.0.0.1` LAN-доступ закрыт.
- Надзор процессов: каждый сервер в своём process group (`setsid`); Ctrl+C/SIGTERM останавливает оба без сирот; смерть одного процесса гасит второй с ненулевым exit. Подтверждено на снимке задачи: после остановки порты свободны и процессов нет; при смерти backend (невалидный порт) frontend погашен, exit ненулевой.
- LAN-доступ проверен curl-ом по реальному LAN-IPv4 (не localhost): `GET /health` → `{"status":"ok","database":"ok"}`, `GET /` → HTML страницы — и в worktree, и в свежем клоне снимка. Открытие страницы с телефона — акт приёмки вехи (владелец), не автоматическая проверка.

## Git hooks

- Установка — `make hooks`: копирование `scripts/hooks/pre-commit` и `scripts/hooks/pre-push` в `$(git rev-parse --git-path hooks)` (копия, не symlink — hooks в общем git-dir не должны зависеть от расположения worktree). Hooks локальны для клона и не версионируются Git.
- `pre-commit` — только staged-файлы (ACMR): `.py` в `backend/` → `ruff check` + `ruff format --check`; `.ts/.tsx/.js/.jsx` в `frontend/` → `eslint` + `prettier --check`. Без релевантных файлов — быстрый exit 0; без E2E. Подтверждено: заведомо плохой `.py` (F401) → commit отклонён, exit 1.
- `pre-push` — backend `pytest -m unit` + `lint-imports`, frontend `npm run test`; без браузеров. Подтверждено: временный падающий unit-тест → push отклонён, exit 1. Hooks не заменяют полный gate публикации (нормативно: [testing](../../rules/testing.md)).

## E2E smoke (Playwright) и полный gate публикации

Введено задачей dunvyr-68c.4. Нормативный состав gate — [testing](../../rules/testing.md) (публикация в `main` — до push: все unit, интеграционные, architecture, frontend tests, E2E smoke desktop+mobile).

- `make test-e2e-smoke` — из `frontend/`: `npx playwright test`. Конфигурация — `frontend/playwright.config.ts`, спеки — `frontend/e2e/`. `@playwright/test` — devDependency `frontend/package.json` (точная версия в lock).
- Два проекта: `smoke-desktop` (Chromium, viewport 1280×720) и `smoke-mobile` (Chromium, `devices['Pixel 5']` — мобильная эмуляция, не реальное устройство). С u4k.5 набор состоит из двух сценариев в обоих проектах: (1) health/smoke — `page.goto('/')` → видимый `h1` «Dunvyr»; `GET /health` через request-контекст → 200 и JSON с полем `status: "ok"`; (2) сквозной сценарий двух гостей (`e2e/two-guests-chat.spec.ts`) — два browser-context: гость A входит псевдонимом → создаёт кампанию → ссылка-приглашение → гость B открывает ссылку → входит и присоединяется → чат в обе стороны → `page.reload()` у A → состав и история чата на месте, каждое сообщение и `member_joined` ровно один раз (`toHaveCount(1)`); второй контекст наследует device-настройки проекта (viewport/userAgent/deviceScaleFactor/isMobile/hasTouch). Подтверждено: 4 passed (2 сценария × desktop + mobile) на настоящем headless Chromium; у исполнителя 3 последовательных прогона без ошибок.
- Оркестрация серверов — Playwright `webServer` (массив из двух записей), команды те же, что в `make dev` (через `mise exec --`): backend — `uvicorn --factory dunvyr.main:create_app` с `cwd: ../backend`, readiness `GET /health`, `DUNVYR_AUTO_MIGRATE=1` и `DUNVYR_ALLOWED_ORIGINS=http://127.0.0.1:<frontend_port>`. Исторически u4k.5 использовал именованную shared-cache in-memory SQLite вместо единственного `StaticPool`-соединения. В кандидате `dunvyr-kye.2` (интеграция ожидается) конфиг создаёт отдельный временный каталог через `mkdtempSync` в `TMPDIR` или системном temp и задаёт backend файловую SQLite `e2e.db` внутри него; на обычном выходе процесса конфига каталог удаляется. Это отдельная БД прогона, не `backend/dunvyr.db`; при аварийном завершении очистка не гарантируется. Frontend — `npm run dev -- --port <port> --strictPort` с `DUNVYR_DEV_HOST=127.0.0.1` и `DUNVYR_BACKEND_ORIGIN=http://127.0.0.1:<backend_port>` (прокси `/api`, контракт `vite.config.ts`), readiness `GET /`. Страница при E2E вызывает `GET /api/identity/me`: без cookie → 401 → рендерится экран входа; `h1` «Dunvyr» остаётся видимым. Playwright останавливает оба сервера после прогона; ранее проверены свободные порты и отсутствие сирот-процессов.
- С u4k.5 `workers: 1` в `playwright.config.ts`: оба smoke-проекта и оба гостя внутри сценария пишут в один backend-процесс и одну БД; последовательный прогон проектов исключает cross-project write contention (параллельный прогон падал на `database table is locked`), скорость прогона остаётся секундной.
- Изоляция E2E: серверы слушают только loopback `127.0.0.1` (LAN не используется); порты `DUNVYR_E2E_BACKEND_PORT` (default **8100**) и `DUNVYR_E2E_FRONTEND_PORT` (default **5273**, он же `baseURL`) отличаются от dev-портов `make dev` (8000/5173) и переопределяются через env (невалидное значение — явная ошибка конфига). Исторический прогон с `8101/5274` — 2 passed; локальный repair `RUN=u4k5repair make test-ci` на default-портах — 4 E2E passed, интеграция ожидается. `reuseExistingServer: false` и `--strictPort`: занятый порт — явная ошибка (подтверждено пробой с `python3 -m http.server 5273` → exit 2 с сообщением), не тихое переиспользование чужого сервера или fallback-порт.
- Установка браузеров — шаг `make setup`: из `frontend/` `npx playwright install chromium` (идемпотентно; один Chromium для desktop- и mobile-проектов), кэш `~/.cache/ms-playwright`; для систем без нужных библиотек документирован `npx playwright install --with-deps chromium` (сам не запускался — библиотек хватило). Подтверждено: `make setup` с чистой worktree установил Chromium, повторный запуск идемпотентен.
- Артефакты прогонов `frontend/test-results/` и `frontend/playwright-report/` игнорируются Git (`.gitignore`) и Prettier (`.prettierignore`).
- `make test-e2e-full` — сейчас запускает тот же Playwright-набор, что smoke: осознанное совпадение при малом числе сценариев (нормативно: [testing](../../rules/testing.md)); расширяется с появлением расширенных E2E-сценариев.
- `make test-ci` — полный локальный gate публикации: `test-unit` + `test-integration` + `test-e2e-smoke` (`test-unit` уже включает architecture `lint-imports` и frontend Vitest). Подтверждено: полный зелёный прогон (6 unit + 4 контракта + Vitest 1/1 + 5 integration + 2 E2E); на снимке u4k.5 — снова зелёный (170 unit + 16 контрактов + Vitest 47 + 76 integration + 4 E2E).

## CI (GitHub Actions): пост-фактум подтверждение публикации

Введено задачей dunvyr-68c.5. Норматив: [testing](../../rules/testing.md) («`main` после push — полный CI-набор»), [development-workflow](../../rules/development-workflow.md) (CI — пост-фактум подтверждение, не замена локального gate до push).

- Workflow — `.github/workflows/ci.yml`, имя `CI`. Триггеры: push в `main` и ручной `workflow_dispatch` (Actions → CI → Run workflow — отладка и проверка стабильности без нового коммита). `permissions: contents: read`; секреты не используются, реальный AI не вызывается.
- Runner `ubuntu-24.04` закреплён сознательно (воспроизводимость образа; Playwright официально поддерживает Ubuntu 24.04), `timeout-minutes: 30`. Actions закреплены мажорными тегами: `actions/checkout@v7`, `jdx/mise-action@v4`, `actions/cache@v4` — без плавающих `@main`.
- Toolchain ставится из того же источника истины, что локально: `jdx/mise-action@v4` читает корневой `mise.toml` (Python, uv, Node), выполняет `mise install` и экспортирует PATH в последующие шаги; кэш mise-инструментов включён по умолчанию.
- Один job `test-ci` нарочно: шаги `make setup` → системные библиотеки Chromium (`cd frontend && mise exec -- npx playwright install-deps chromium` — runner-специфика, локальные команды не меняются) → `make test-ci`. Запускаемый набор — буквально та же цель `make test-ci`, что и локальный gate (unit + architecture + Vitest + integration + E2E smoke), один общий снимок и порядок шагов.
- Кэши `actions/cache@v4`: `~/.cache/uv` (ключ по `backend/uv.lock`), `~/.npm` и `~/.cache/ms-playwright` (ключи по `frontend/package-lock.json` — версия `@playwright/test` зафиксирована в lock); смена lock-файла автоматически сбрасывает кэш.
- Изоляция на runner: E2E-серверы поднимает сам Playwright `webServer` на loopback (8100/5273); вариант SQLite зависит от снимка конфига (см. раздел E2E выше) — внешние env-переменные и порты runner не нужны; `reuseExistingServer: false`.
- Контракт workflow подтверждён статически: `actionlint` 1.7.12 — exit 0, независимый YAML-парс — exit 0, referenced-цели `make setup`/`make test-ci` сверены с Makefile. Фактический прогон на GitHub происходит пост-фактум после публикации (природа CI); наблюдение — раздел Actions репозитория.

## Ограничения (ещё не существует)

CORS/allowed origins на backend настроены задачей dunvyr-u4k.1 (allow-list `DUNVYR_ALLOWED_ORIGINS` + Origin-проверка POST + Vite-прокси `/api` в dev) — контракт: [backend/identity](../backend/identity.md). mise-таски-делегаты сознательно не заведены (Makefile — единственный публичный интерфейс). Одновременный прогон `make dev` и E2E не проверялся — доказаны только раздельные порты и env-переопределение; mobile — эмуляция устройства в Chromium; Playwright предупреждает, что ОС не officially supported (использована fallback-сборка chromium Ubuntu 24.04).

Историческое ограничение u4k.5: named SQLite URI shared-cache использовал неявный выбор pool SQLAlchemy с предупреждением об устаревании; кандидат dunvyr-kye.2 использует для E2E временный файл, как описано выше.
