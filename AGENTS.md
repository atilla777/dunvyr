> Это **проект-потребитель MIS**, не исходный репозиторий MIS. Читай применимые правила перед изменениями; не заменяй MIS собственной процедурой SDLC.

## Источники истины

1. [OKF-карта документации](docs/index.md) — точка входа (Open Knowledge Format 0.2).
2. [Продуктовые требования](docs/product/index.md) — **что** строится, ограничения MVP и принятые решения. Не переписывать автоматически под существующий код.
3. [Инженерные правила](docs/rules/index.md) — **как** строится и проверяется система. Обязательны.
4. [Спецификации реализованного поведения](docs/spec/index.md) — дополняются по мере реализации; не создавать по одной на каждую задачу.
5. **Beads** — конкретные Epic/Task/Bug, критерии и зависимости, выработанные при планировании; не дублировать tracker в файлах.

Читай целевые документы, а не весь пакет при каждой задаче. При противоречии высокого уровня не выбирай молча трактовку: сообщи о конфликте. Подробное правило приоритетов — [управление знаниями](docs/rules/knowledge-and-sdlc.md).

## Рабочий процесс: установленный MIS

Устанавливать MIS только явно по проверенной процедуре из [README MIS](https://github.com/atilla777/mis), с фиксацией точного SHA; установка не выполняется самим AGENTS.md. Для применения нужен OpenCode 2.x с native worktree/session, Beads `bd`, embedded Dolt, Git remote, профили агентов `standard` и `advanced` (конкретные модели выбирает владелец). Не придумывать `mis.yaml`, дополнительные адаптеры или альтернативный трекер.

После фактической установки доступны `/mis-install`, `/mis-plan`, `/mis-run`, `/mis-bug`, `/mis-status`, `/mis-update`. Не вызывать неизвестные скиллы и не запускать `/mis-plan` или `/mis-run`, пока окружение и обязательные проверки не готовы. `/mis-install` не создаёт приложение и не выбирает стек.

Планирование — минимальные проверяемые вертикальные срезы, native Epic/Task/blocks в Beads. Реализация — выделенная worktree, затронутые проверки, независимый read-only AI-review; обновить `docs/spec/` при появлении устойчивого проверенного поведения. [Стратегия тестирования](docs/rules/testing.md), [workflow Git и публикация](docs/rules/development-workflow.md).

**Граница публикации:** агент интегрирует изменения в `main` **только** через установленный протокол MIS (`mis-proj-op-publish-change`): полный обязательный gate на интегрированном снимке, независимый read-only AI-review, non-force push с read-back. Запрещены force push, переписывание опубликованной истории, обход проверок и ложные отчёты о результатах. Закрытие Task означает подтверждённую публикацию, а не продуктовую приёмку; приёмка остаётся за владельцем (решение о режиме прямой публикации в `main` принято владельцем 2026-11-05). Запрещено скрытно менять установленный MIS, обходить его условия завершения или закрывать задачу ложным утверждением.

## Инварианты архитектуры и продукта

- **Bounded Context first**, а слои внутри каждого контекста: [карта доменов](docs/rules/bounded-contexts.md), [архитектура](docs/rules/architecture.md).
- Строгие публичные контракты; ни импорт чужих внутренних модулей, ни изменение чужих таблиц/репозиториев. Автоматические архитектурные тесты.
- Чистый Domain без FastAPI, Pydantic, SQLAlchemy и LLM SDK. Однопроцессный модульный монолит; НЕ микросервисы.
- Сервер — источник истины об игровых состояниях и правилах. LLM не пишет данные и не назначает произвольные сюжетные последствия. [Правила AI](docs/rules/ai-integration.md).
- Персонажи и кампании сохраняются; сохранение в SQLite, real-time через WebSocket; мобильный UI — часть MVP.
- Секреты сценария, скрытые решения и неизвестные локации не выдавать клиенту до раскрытия. [Безопасность](docs/rules/security-and-privacy.md).
- Стек и проектные интерфейсы зафиксированы в [engineering stack](docs/rules/technology-and-infrastructure.md). Не вводить инфраструктуру сверх MVP без причины.

## Проверки и полномочия

До начала изменения определяй затронутые Bounded Contexts и потребителей их публичных контрактов; перед публикацией приложи фактические результаты тестов, ревью и ограничения. Локально: тесты затронутого поведения; быстрые Git hooks; перед публикацией в `main` — полный обязательный gate (все unit, интеграционные, architecture, frontend тесты, E2E smoke), после push — CI GitHub Actions; расширенные E2E по риску или на приёмке MVP.

**Команды `make ...` в [testing.md](docs/rules/testing.md) — целевые контракты для будущего bootstrap, а не уже существующие команды.** Пока скелет приложения и Makefile не созданы, не заявляй, что проверки выполнены.

Разрешения на commit/push, публикацию в `main`, изменение CI и Beads/Dolt-публикацию определяются реальными полномочиями и согласованным workflow; опасные операции, force push, переписывание опубликованной истории и обход branch protection не разрешены этим файлом.
