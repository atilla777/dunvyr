# Архитектура модульного монолита

## Слои внутри Bounded Context

Рекомендуемая, но **не обязательная для пустых каталогов**, структура:

```text
<bounded-context>/
  domain/          # Чистые Entity, VO, инварианты, domain services/events
  application/     # Use cases, оркестрация, порты, транзакционные границы
  infrastructure/  # SQLAlchemy adapters, LLM or I/O adapters (по владению)
  presentation/    # FastAPI роутеры, WebSocket handlers, HTTP DTO boundary
  public/          # Единственный вход для других контекстов
```

`domain` не импортирует application, infrastructure, presentation, FastAPI, Pydantic, SQLAlchemy, WebSocket или AI SDK. `application` зависит от domain и абстракций, но не от конкретного хранилища. `infrastructure` реализует абстракции, composition root связывает их в FastAPI dependencies. Междоменные запросы только через public contracts.

## Прямая операция и событие

- **Команда / Query:** точный запрос через публичный интерфейс, когда нужен конкретный ответ или согласованное действие (получить навыки, применить урон).
- **Доменное событие:** immutable факт уже произошедшего (`EncounterCompleted`, `SkillCheckResolved`, `StoryFactRevealed`). Внутрипроцессная синхронная обработка для обязательных согласованных изменений, без Redis/RabbitMQ/Kafka в MVP.
- Для игровых эффектов, зависящих от нескольких контекстов, **application orchestrator** определяет порядок и транзакцию; не делать скрытых side effects в ORM callbacks.
- События не являются заменой explicit use case или магической eventual consistency. Связанные данные должны быть консистентны.

## Транзакционность и доставка

1. Проверить полномочия, состояния, конкурентную версию команды.
2. Выполнить проверки правил; броски и их значения зафиксировать в составе разрешаемого действия.
3. Применить изменения через owning contexts в **одной короткой транзакции** там, где они должны быть атомарны (общая SQLite и один process).
4. Сохранить события и commit.
5. **Только после commit** отправлять WebSocket/другие внешние уведомления. При ошибке доставки состояние не откатывать; клиент должен уметь восстановить snapshot и пропущенные события.

Сеть и LLM не вызывать во время удержания write-транзакции. Команды, способные повториться из-за retry/reconnect, должны иметь idempotency key или эквивалентный механизм не-дублирования. Отладочные логи не заменяют durable story state/audit.

## Конкурентность

У одной кампании должна быть строгая последовательность записи игровых команд; обработка двух подтверждений одного хода, двух голосований или двойное начисление XP недопустимы. Для SQLite предусмотреть atomic compare-and-swap по версии записи либо сериализацию команд кампании на сервере и проверку версии в транзакции. Одни Python mutex без защиты на уровне БД недостаточны для общего случая.

## Архитектурные проверки

Использовать Import Linter (или сопоставимый инструмент) с контрактами: независимость публичных доменных пакетов, запрет импорта чужих `domain/application/infrastructure`, слоёвость `domain <- application <- adapters`. Дополнительно тестами подтверждать отсутствие прямой записи в чужие таблицы и корректность transactional use cases; импорты одни этого не доказывают.

## ADR

Если решение меняет границы contexts, владение данных/транзакций, формат публичных API или принятый архитектурный принцип — зафиксировать краткий ADR в `docs/rules/architecture/adr/` **только при реальном решении**, не создавать пустую коллекцию ADR ради шаблона.
