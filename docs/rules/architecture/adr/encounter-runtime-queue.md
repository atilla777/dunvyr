# Runtime испытания и очередь

Решение bounded-среза `dunvyr-lbp.4`, продолжение
[границы каталога шаблонов](encounter-template-catalog.md).

- `adventures` владеет immutable template и доступностью. `gameplay` получает
  только `AvailableEncounterCatalogReader` и сохраняет ID выбранного испытания,
  не полный шаблон, условия, исходы или private metadata. Runtime и единственная
  очередь принадлежат `gameplay`, ключ — кампания, не объект и не встреча.
- Стартовать может участник со своим допустимым сохранённым персонажем во время
  running-встречи. `characters.public.CharacterEligibilityReader` возвращает
  только ID гостя и персонажа; owning adapter проверяет принадлежность и карточку
  по закреплённым правилам создания. Ростер фиксируется при старте: все участники
  кампании с допустимыми персонажами, включая offline, по `(joined_at, guest_id)`.
  Позднее подключение/создание персонажа состав уже начатой очереди не меняет.
- Порядок базового раунда сохраняется. Обмен текущего online-игрока возможен
  только с более поздним непройденным online-слотом текущего раунда. Смена мест
  не расходует действие и не создаёт новое. В следующем раунде базовый порядок
  восстанавливается. Исполнение действий, ручной пропуск, броски и резолюция
  отсутствуют в этом срезе.
- Offline-слоты автоматически помечаются пропущенными без наград. Нормализация
  ограничена длиной ростера: полностью offline раунд исчерпывается и ждёт, без
  бесконечных пустых раундов. Подключение после сохранённого пропуска не возвращает
  слот назад; после исчерпания создаётся максимум один следующий раунд.
- Paused и ended встречи замораживают очередь. Resume или новая running-встреча
  продолжают тот же runtime и затем нормализуют актуальное присутствие. End не
  завершает испытание и не сбрасывает прогресс. После рестарта очередь читается
  из SQLite; свежий пустой presence может один раз исчерпать текущий раунд.

## Транзакция и конкурентность

Composition root связывает все owning adapters **одним SQLAlchemy Session**.
Перед чтением lifecycle, ростера, карточек и шаблонов gameplay вызывает
`campaigns.public.CampaignGameplayAccess.lock`: campaigns-owned UPDATE получает
SQLite writer lock, тот же, что lifecycle-команды. Gameplay не импортирует
foreign ORM и не знает имён чужих таблиц. Его собственные записи дополнительно
защищены PK кампании и CAS по версии, receipts — PK `(campaign, actor, key)`.

Порядок блокировок — **DB writer → короткий presence guard**. Guard повторно
учитывает lease/grace и не позволяет connect/disconnect/expiry пересечь снимок
online до commit. Внутри нет await, сети или рассылок; только вычисление и
короткие SQL-операции. Presence уведомления выходят после освобождения guard.
Регистрация reconnect до снимка сохраняет ещё непропущенный слот; регистрация
после commit следует уже сохранённому пропуску. Несколько вкладок дают один ID.

Очередь, точный ответ receipt и `queue_changed` в durable communication stream
фиксируются одной транзакцией. Повтор того же ключа тем же актором возвращает
исходный ответ, даже после последующих изменений; другой payload — conflict.
Команды проверяют одновременно queue version и lifecycle revision. Ошибка
staging/receipt/commit откатывает весь набор. Только после commit notifier
перечитывает событие и рассылает; сбой доставки не отменяет прогресс.

Нормализация автономна: lifespan периодически перечисляет сохранённые очереди,
выполняет DB-работу вне event loop, отдельной транзакцией на кампанию. Сбой
одной кампании журналируется и не блокирует другие; следующие проходы повторяют
попытку даже без HTTP и presence callbacks. Остановка ждёт текущую работу.
HTTP read не является единственным драйвером прогресса.

## Доставка и восстановление

Членам кампании доступны start/swap/read; cookie-session, Origin/CSRF-защита,
строгие DTO, UUID idempotency key и отдельный rate limit обязательны.
Очередь имеет монотонную `version`. Событие разделяет sequence с чатом и
lifecycle; каждый member-only chat snapshot содержит полный `queue_state`
независимо от cursor и последних 200 событий. Клиент соединяет snapshot/live
по версии, не откатывая состояние старым receipt или запоздалым кадром.
Существующий subscribe-before-accept и snapshot после WebSocket open сохраняются.
Гарантия доставки best-effort с восстановлением из SQLite, не exactly-once.

## Transient SQLite в тестах и smoke

`StaticPool` для in-memory SQLite предоставляет одну DBAPI connection, а не
независимые транзакции нескольким Session. С появлением фонового DB-reader даже
закрытие такого reader может откатить текущую HTTP-запись. Composition root
сериализует корневые транзакции app Session-factory для этого single-connection
режима; блокировка общая для app-factories одного Engine и освобождается после
реального commit/rollback/close. Это техническая совместимость transient-mode,
не замена owning DB-lock/CAS: файловая SQLite использует независимые connection,
а конкурентность start/swap/lifecycle/reconnect отдельно проверяется на файле.
