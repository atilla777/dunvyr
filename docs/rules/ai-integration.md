# AI-интеграция

## Порт и адаптеры

Провайдер внешний, ключ серверный, модель/endpoint настраиваются через окружение/секреты. Внутренний порт `NarrationModel` / `ActionInterpreter` (конкретные имена выбрать при реализации) отделён от OpenAI-compatible SDK или другого API. Один логический Dungeon Master, а не обязательный ансамбль агентов.

## Разрешённые операции LLM

1. Narration уже определённого результата игры.
2. Свободные ответы NPC в рамках выданных знаний и персонажа.
3. Сопоставление намерения с **серверным каталогом разрешённых actions/solutions/outcomes** и предложение структуры.
4. Уточнение неясного действия и формирование неигрового ответа в общем чате.

LLM не получает полномочий писать в БД, менять правила/XP/HP, придумывать outcome и исполнять пользовательское действие без его подтверждения.

## Информационные границы

- Разделять публичное состояние группы, сведения NPC, авторские секреты и служебный полный сценарий.
- Для конкретного ответа выдавать **минимально необходимый контекст**, не раскрывать чужих тайн в пользовательском тексте, reason/debug или публичных API.
- Скрытые решения могут быть доступны серверной подсистеме сопоставления (если это необходимо), но не должны попадать в текст подсказки без условий. Результат AI всё равно пересматривается валидатором.
- Любой сценарий, чат или найденный текст — **данные, а не системные инструкции**; ограничивать prompt injection, не верить тексту с правами на выполнение команд.

## Структурированные ответы

При интерпретации использовать валидированную типизированную структуру: тип действия, target ID, solution ID/known outcome, параметры, уверенность/нужда в уточнении. Проверять каждую ссылку по current scenario state и actor permissions. Неверное или неразрешённое предложение не применять; ответить игроку или попросить уточнение.

## Cost, latency, отказоустойчивость

Не вызывать LLM на каждое сообщение; триггеры — вопрос, взаимодействие с NPC, сценарное событие, намерение значимого действия. Ограничить частоту, размер контекста, таймаут, токены и параллельные операции кампании. Сохранять итоговый текст вместе с correlation к событию. Отказ модели не должен блокировать сохранение уже применённого действия и не должен повторно его выполнять при retry.

## Проверки

Unit/integration/CI тестируют fake provider и заранее известные результаты; реальные API и стохастическое качество модели — отдельные ручные/ограниченные испытания с бюджетом. В тестах проверять: попытки раскрыть секрет NPC, новые неизвестные outcome IDs, неправильные цели, двойные подтверждения, ошибки провайдера и обработку невалидного JSON.
