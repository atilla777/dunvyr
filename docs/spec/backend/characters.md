# Персонаж участника кампании

> Кандидат Beads `dunvyr-kye.3` дополняет `dunvyr-kye.2`; интеграция ожидается. Продуктовый источник — [персонажи](../../product/characters.md), правила доступа — [безопасность](../../rules/security-and-privacy.md); шаблоны берутся из [закреплённого приключения](adventures.md), версия правил — [ADR](../../rules/architecture/adr/character-creation-policy.md). Владелец принял для этого среза одного собственного персонажа на кампанию без удаления и пересоздания. Числа ниже — ограниченное правило задачи, не окончательный баланс.

## Контракт

Маршруты `/api/campaigns/{campaign_id}` определяют гостя по серверной сессии и проверяют членство; клиент не выбирает владельца. Аноним и не-участник получают `403 forbidden`. Организатор использует те же операции для своего персонажа, административного изменения чужого нет.

- `GET /character-templates`: до выбора приключения `{"status":"waiting","archetypes":[]}`, после — `status: "ready"`, массивы `archetypes` и `skills` из закреплённого снимка, у каждого архетипа добавлен `budget`. Объект `creation_rules` содержит `id: "archetype-budget-v1"`, `minimum: 0`, `maximum: 10`, `relative_limit: 1`, `characteristic_cost: 2`, `skill_cost: 1`. Навык включает свою неизменную `characteristic`. Сценарные локации и ресурсы не возвращаются. Внутренний immutable `PinnedTemplatesReader` читает снимок, не текущий каталог.
- `GET /character`: собственная карточка либо JSON `null`, если её нет.
- `POST /character`: строгий объект со строками `name`, `appearance`, `archetype_id` и необязательным объектом `allocation`; дополнительные поля, включая владельца, запрещены. В `allocation` обязательны `characteristics` с ровно четырьмя ключами `strength`, `agility`, `intellect`, `presence` и объект `skills` с ID навыков и целочисленными значениями; `null` не допускается. Без `allocation` используются значения архетипа. Сервер обрезает пробелы по краям имени и внешности, допускает соответственно 1–60 и 1–2000 символов, запрещает Unicode-категории `C` (в том числе управляющие символы). Архетип должен присутствовать в снимке. Ответ содержит `id`, `campaign_id`, `guest_id`, имя, внешность, ID и название архетипа, `characteristics` и `skills` (ID, название, значение).
- Правило `archetype-budget-v1`: каждое значение — строго целое число от 0 до 10 и отличается от базового значения архетипа не более чем на 1; для отсутствующего в архетипе навыка база равна 0. Отсутствующий в запросе навык считается равным 0, а не базовому значению. Разрешены только ID навыков сеттинга; привязку к характеристике запрос не меняет. Цена распределения — удвоенная сумма характеристик плюс сумма навыков; она не превышает цену штатного архетипа. Неизрасходованный бюджет допускается, права потратить его позднее не создаёт. Проверку выполняет сервер до записи.
- Первое создание — `201`, повтор с теми же нормализованными именем, внешностью, ID архетипа и распределением — `200` с той же карточкой; при сравнении отсутствующий и нулевой навык эквивалентны. Другой допустимый запрос после создания — `409 character_conflict`. Без выбранного приключения — `409 adventure_required`; невалидная структура — `422 invalid_request`, невалидные значения или неизвестный архетип — `422 invalid_character`. POST требует разрешённый Origin (`403` при отсутствии или запрете); отдельный in-process лимит на IP — 10 запросов за 60 секунд, при превышении `429 rate_limited` с `Retry-After`, счётчик сбрасывается при рестарте.

## Хранение и границы

Миграция `0007` создаёт `characters_characters` с составным первичным ключом `(campaign_id, guest_id)` и JSON-содержимым. Вставка с защитой от конфликта обеспечивает одного победителя; совпадающий параллельный запрос получает replay. Карточка переживает перезапуск на файловой SQLite; прежние карточки читаются без переписывания. Редактирование после создания, удаление и пересоздание, HP, XP, предметы и игровой контроль в этом срезе не реализованы; это не отменяет продуктовые требования.

## Проверки кандидата

`backend/tests/unit/test_characters_domain.py` проверяет текст, бюджет, границы, типы и неизвестные ID; `backend/tests/unit/test_characters_architecture.py` — отсутствие литеральных имён чужих таблиц в characters и чувствительность этой защиты к запрещённым чтению и записям (динамически собираемые имена она не обнаруживает). `backend/tests/integration/test_characters.py` проверяет ACL, Origin, валидацию без побочных эффектов, штатные и настроенные карточки, нормализованный replay, конкуренцию, прежние данные, закреплённый снимок и рестарт. `frontend/src/CharacterPanel.test.tsx` проверяет расчёт, границы, ошибку и карточку; `frontend/e2e/adventure.spec.ts` — двух настроенных персонажей, чат и reload на desktop и mobile-эмуляции. На переданном проверенном кандидате прошли `make lint` и `make test-ci`; интегрированный снимок ещё не проверен. Полное соблюдение TDD не утверждается: один тест типа навыка добавлен позднее реализации.

## Допустимость для очереди

Кандидат `dunvyr-lbp.4`: `characters.public.CharacterEligibilityReader` предоставляет gameplay только идентификаторы владельца и допустимого сохранённого персонажа; проверка принадлежности и валидности карточки остаётся у characters. Отсутствующая или повреждённая карточка не допускается к стартовому ростеру; начать можно только со своим допустимым персонажем. Контракт очереди — [gameplay](gameplay.md).

Кандидат `dunvyr-lbp.6`, интеграция ожидается: `CharacterCheckInputReader.check_input` проверяет собственную сохранённую карточку и её политику по закреплённым шаблонам, ID персонажа и навыка; возвращает только значения фиксированной характеристики и навыка (отсутствующий навык — 0), либо `None`. Это внутренний порт, не клиентский API и не разрешение обходить проверку членства. См. [подтверждение](gameplay.md#подтверждение-и-небоевой-результат).
